## 1. 背景、问题与机会

### 1.1 背景：Agent 正在从"玩具"走向"生产力"

2024 年以来，以 Deep Agents（LangGraph 系）为代表的智能体框架已经解决了单 Agent 的核心能力问题——文件系统、技能、记忆、工具调用、多步推理都趋于成熟。**但"让一个 Agent 干活"从来不是真正的瓶颈。**

真正的瓶颈在别处：

> 一个公司要的不是"一个会写代码的 AI"，而是"一群分工明确、各司其职、又能在项目里互相协作的 AI 同事"——以及一套能管住它们（谁、干什么、花了多少钱、有没有越界）的管理体系。

AgentCore 判断：**Agent 落地的下一站是「多智能体治理与管理平面」，而非更强的单 Agent。**

### 1.2 我们观察到的问题（Problem Statement）

| # | 问题 | 证据 / 现状 |
|---|------|-------------|
| P1 | **多 Agent 无从管理** | 每个 Agent 是独立配置 + 独立进程，缺乏统一控制台；配置靠手写 `agent.json` |
| P2 | **Agent 之间不会协作** | 复杂任务超出单 Agent 上下文/能力边界，只能人工在多个 Agent 间搬运结果 |
| P3 | **自主 AI 令人不安** | Agent 有读写删文件、调工具、联网的能力，但缺少"谁能做什么、危险操作要审批"的护栏 |
| P4 | **成本与行为不可观测** | 不知道哪个 Agent 在烧 token、跑了多少、成功了没有、出错了为什么 |
| P5 | **重复造轮子** | 模型 Key、技能、外部工具（MCP）、环境配置在每个 Agent 里重复配置、各自为政 |

### 1.3 机会窗口（Why Now）

- **Deep Agents 已成熟**：文件系统/技能/记忆/HITL/子代理等能力已产品化（见说明书 §4），我们只需在其上做"管理 + 编排 + 治理"，不必重造引擎。
- **市场空白**：LangSmith 等偏部署与开发者可观测性；Chatbot 类偏单会话。**"面向业务的多 Agent 管理平面"** 仍是差异化空位。
- **企业合规压力**：越来越多组织要求 AI 使用"可审计、可审批、可隔离、可计费"，这恰恰是治理平面的价值点。

### 1.4 产品目标（What Success Looks Like）

- **G1（采用）**：非技术用户能在 10 分钟内创建一个可用 Agent。
- **G2（协作）**：用户能组建"多 Agent 团队"，让它们互相委派完成一个跨能力任务。
- **G3（安全）**：所有危险操作默认受控——工作区隔离、权限规则、高风险动作人工审批。
- **G4（治理）**：管理者能按 Agent 查看成本、状态、变更历史，并回收权限。
- **G5（开放）**：一次配置，即可接入任意模型、技能、MCP 工具。

## 2. 目标用户与需求

### 2.1 用户角色矩阵（含职责与决策权）

| 角色 | 一句话 | 核心职责 | 决策权 |
|------|--------|----------|--------|
| **R1 业务用户** | 用 AI 干活的人 | 对话、使用 Agent 完成工作 | 使用 Agent、新建个人 Agent |
| **R2 开发者** | 扩展 Agent 能力的人 | 接 MCP、写技能、配模型 | 配置工具/技能/MCP |
| **R3 团队管理者** | 对结果负责的人 | 建团队、分 Agent、看成本 | 审批高危操作、分配权限、启停 Agent |
| **R4 平台运维** | 保证系统可用的人 | 部署、备份、监控、排障 | 系统级配置、恢复 |

### 2.2 用户故事（User Story，带验收提示）

**R1-001｜新建个人助理**
> 作为业务用户，我想在页面上创建一个人格化助理，它知道我叫什么、喜欢什么风格，这样我不必每次重复背景。  
> 验收：创建后可引导填写身份偏好（写入 `agent.md` / `memory/USER.md`），后续对话记住这些偏好。

**R1-002｜跨任务协作**
> 作为业务用户，我想要让我的"全能助理"把我手头的英文文档翻译成中文并整理成周报，这样我不必自己复制粘贴。  
> 验收：全能助理能委派给 `翻译` 与 `文案` 两个专精 Agent，主对话只看到最终结果，不看到中间过程。

**R1-003｜结果可追溯**
> 作为业务用户，我想回顾我上周和某个 Agent 聊了什么、它改过哪些文件，这样我能找回当时的成果。  
> 验收：会话历史可回放，文件变更可在 Files 页查看。

**R2-001｜接入外部工具**
> 作为开发者，我想给 Agent 接上公司的数据库 MCP 服务，这样 Agent 能查真实业务数据。  
> 验收：在 Mcp 页配置后可被该 Agent 调用，且可通过权限规则限制其访问范围。

**R2-002｜能力沉淀**
> 作为开发者，我想把一个 Agent 的领域知识固化成技能（Skill），这样其他 Agent 也能复用。  
> 验收：技能进入 SkillPool，可被多个 Agent 的 `skills/` 目录引用。

**R3-001｜高危操作审批**
> 作为团队管理者，我想对"删除工作区文件"这类操作设置人工审批，这样 Agent 不会误删重要数据。  
> 验收：Agent 触发该操作时对话暂停并出现审批卡片，可批准/编辑/拒绝，且决策被记录。

**R3-002｜成本掌控**
> 作为团队管理者，我想按 Agent 查看 token 消耗和成本，这样我能知道钱花在哪、谁在烧钱。  
> 验收：TokenUsage 页按 Agent/时间维度统计。

**R4-001｜可靠运行**
> 作为运维，我想看到所有 Agent 的健康状态并能一键备份恢复，这样系统出问题我能快速恢复。  
> 验收：Heartbeat 展示健康度，Backups 可导出/导入。

### 2.3 用户痛点 → 需求映射

| 用户痛点 | 对应需求 | 归属模块 |
|----------|----------|----------|
| "配置 Agent 太技术" | 零代码可视化创建/配置 | Agents / AgentConfig |
| "单 Agent 干不完" | 跨 Agent 子代理委派 | Chat（委派） |
| "怕它乱删乱改" | 文件隔离 + 权限规则 + HITL 审批 | Files / Security / HITL |
| "Key 到处散" | 环境变量中心 | Environments |
| "不知道谁在烧钱" | Token 成本看板 | TokenUsage |
| "重复配模型/技能" | 模型中心 + 技能池 + MCP 复用 | Models / SkillPool / Mcp |

```
│Chat  │  引导对话      │ 引导 │ 文案（选择模型 │协作  │  派活：      │看板 │
└──┬──┘                │  │  │ /工具/人格）    │  │  │  "写英文周报" │  │  │

   ▼                    ▼                    ▼  ▼  ▼              ▼  ▼
 建立个人助理      建立专精 Agent 团队    全能助理按需调度子代理    看 Token/状态

```

**旅程关键节点与对应要验证的假设：**

| 阶段 | 关键动作 | 我们要验证 | 若失败 |
|------|----------|-----------|--------|
| 发现 | 欢迎对话引导 | 用户理解"我能让 AI 干活" | 引导文案太技术 |
| 上手 | 创建专精 Agent | 用户理解"Agent = 有分工的 AI 同事" | 创建向导太复杂 |
| **协作** | 全能助理委派子代理 | 用户体验"1+1>1 的协作"（**Aha**） | 子代理 description 太弱导致委派不准 |
| 治理 | 看成本/状态 | 用户信任"可控" | 无认证/无审批闭环 → 不敢放权 |

### 3.3 关键流程设计

#### 流程 A：创建 Agent

```
用户在 Agents 页点击"新建"
   │
   ├─(1) 填基础信息：名称、人格(system prompt)、一句话用途
   ├─(2) 选模型（默认走模型中心默认值，可选其他供应商）
   ├─(3) 选内置工具（默认最小集，可勾选/排除）
   ├─(4) 选技能（从 SkillPool 引入，可选）
   ├─(5) 配权限（默认：仅工作区可读写，可自定义规则）
   ├─(6) 设置委派开关 enable_subagents（默认关，安全优先）
   └─(7) 确认创建 → 生成独立工作区 + agent.json → 进入可对话状态
```

#### 流程 B：跨 Agent 委派（当前已实现，见通讯机制报告）

```
用户在 Chat 选 default（enable_subagents=true）→ 发消息
   → 图构建时注入其他 Agent 为 SubAgent（task 工具）
   → default 的 LLM 决定委派 task(subagent_name, description)
   → SubAgentMiddleware 进程内执行子代理（隔离上下文）
   → 仅最终文本回传给 default → default 整合后回复用户
```

#### 流程 C：HITL 人工审批（产品目标态；当前仅配置层就绪）

```
用户配置"删除文件需审批"
   → Agent 触发 delete → SDK 触发 interrupt_on → 对话暂停
   → 前端检测到 interrupt → 弹出审批卡片（显示动作/参数/原因）
   → 用户选：批准 / 编辑参数后批准 / 拒绝
   → 决策回写 checkpointer → Agent 继续执行
   → 本次决策写入审计日志
```

- **验收**：
  - [ ] 同一会话内多轮上下文连续（checkpoint 恢复）

- **描述**：`enable_subagents=true` 的 Agent 可把任务委派给其他 Agent（SDK `task` 工具）。

- **当前差距**：子代理仅 3 字段（name/description/system_prompt），**无法**为子代理单独配工具/模型/权限（见 §5.3 待优化项）。

- **状态**：⬜（配置层已支持，运行时闭环未接通——最高优先级）

## 5. 核心机制的产品化设计（关键差异化深挖）

### 5.1 "AI 员工团队"心智模型

产品希望用户建立的类比：

| 现实世界 | AgentCore 映射 |
|----------|----------------|
| 招聘员工 | 创建 Agent（给身份、人格、分工） |
| 员工工位/电脑 | 独立工作区（虚拟文件系统隔离） |
| 岗位职责/权限 | 权限规则（谁能读写什么、什么要审批） |
| 团队协作 | 跨 Agent 委派（task 工具） |
| 考勤/成本/绩效 | 状态机 + Token 看板 + 会话追踪 |
| 辞退/转岗 | 删除/修改 Agent 配置 |

> 这个心智模型是产品所有交互文案、引导、模板的设计主轴——**我们卖的不是"Agent 配置器"，而是"AI 员工团队管理系统"。**

### 5.2 为什么"跨 Agent 委派 + 上下文隔离"是产品护城河

单 Agent 产品容易复制，但**编排一群专精 Agent 并让它们协作**有真实的工程与产品壁垒：
1. **上下文隔离**：委派只回传结果，主对话不被中间过程污染（Deep Agents 核心价值）。
2. **专精 vs 全能**：用户能为不同任务养不同"专家"，而非一个臃肿的万能 Agent。
3. **成本弹性**：简单子任务可用便宜模型（当前未支持，见 5.3）。
4. **安全边界**：每个 Agent 独立工作区，委派不越权（需 SubAgent 权限收窄支撑，见 5.3）。

### 5.2.1 多智能体协作模型（收敛基线，方案 A）

> **本节要回答的问题**：产品里"主 Agent / 子 Agent"到底怎么表达？主 Agent 怎么发现和调用新建的子 Agent？多个 Agent 之间怎么通讯？
> **核心结论（一句话）**：AgentCore 采用 **「能力开关 + 声明规格 + 图重建」** 的主从协作模型——不做硬主/子分类，创建子 Agent 是声明规格而非启动进程，动态发现靠新建后触发主 Agent 图重建。
> 本节是方案 A 的实现基线，也是后面 §5.3 差距表、§6 业务规则、§7 版本规划的依据。

#### ① 总体模型图：主从 + 角色切换

先看两个视角，帮建立直觉：

**视角 1 — 拓扑：扁平主从（SDK 原生）**
```
                 ┌───────────────────────────┐
                 │        主 Agent           │
                 │  (supervisor, 可委派别人)  │
                 └────────────┬──────────────┘
                              │ task 工具
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        ┌──────────┐   ┌──────────┐   ┌──────────────┐
        │ 内置通用  │   │ 自定义子A │   │ 自定义子B     │
        │general-  │   │  (专精)   │   │  (专精)       │
        │ purpose  │   └──────────┘   └──────────────┘
        └──────────┘
```
- 主 Agent 内置 `task` 工具 + 一个内置 `general-purpose` 子 Agent。
- 自定义子 Agent 通过 `subagents=[...]` 追加；**同一层、同一注册表，无嵌套**（子 Agent 不能再派生子 Agent）。

**视角 2 — 角色切换：同一个 Agent 身兼两职**
```
 用户直接对话 B 时：  B 是「主」          B 调别的 Agent
 被 A 委派时：        B 是「从」          B 被 A 的 task 调用
        ┌─────────────────────────────────────────────┐
        │   Agent B（本身是完整的可对话图）             │
        │   ├─ 用户选中它对话  → B 是主，可委派别人    │
        │   └─ 被 Agent A 委派 → B 是从，被 A 调用     │
        └─────────────────────────────────────────────┘
```
> **关键认知**："主 / 从"是**某次调用关系里的角色**，不是 Agent 的固有属性。同一个 Agent 既是主又是从，取决于"谁在调用谁"。

#### ② 主/子模型：能力开关，而非类型标签

**设计原则**：不做"主 Agent 类型 / 子 Agent 类型"的硬分类，改用三个**能力开关**表达角色。

| 能力开关 | 默认 | 含义 | 对应 UI |
|----------|------|------|---------|
| **可被用户对话** | 开 | 决定是否出现在左上角选择页 | 选择页列表项 |
| **委派开关** `enable_subagents` | 关 | 决定它能否调用别人（当"主"） | 委派开关 |
| **可被委派**（可委派给哪些主 Agent） | 关 | 决定它是否出现在别人委派列表（当"从"） | 可见性配置 |

**落到 UI**：
- 左上角选择页用**分组视图**（"我的团队"按可委派主 Agent / 全部），而非硬隐藏子 Agent——保留子 Agent 单独对话能力。
- 一个 Agent 勾选"委派开关" → 它是"主"；勾选"可被委派" → 它是"从"；两者可同时勾选。

#### ③ "提前创建"的正确语义：声明规格，而非启动进程

**最容易误解的点**：deepagents 里**没有"启动 Agent 进程"这个概念**。

```
❌ 误解：创建子 Agent = 启动一个常驻运行的 Agent 进程
✅ 正解：创建子 Agent = 声明一份"规格"（姓名/职责/能力/权限）
   —— 真正运行时，主 Agent 每次 task 调用才临时构建一个全新实例
   —— 该实例无状态、跑完即销毁（ephemeral）
```

- **"创建子 Agent" = 提前声明其规格**：`name` / `description` / `system_prompt`，并补全 `tools` / `model` / `permissions` / `interrupt_on`。
- **UI 不用"启动"按钮**（避免用户误以为子 Agent 常驻烧钱），改用 **"应用配置 / 刷新委派"**，其真实语义是"让主 Agent 图重建以应用新配置"。

#### ④ 动态发现：新建子 Agent 后如何让主 Agent 附加它

**为什么不能纯动态**：SDK 的 subagent 是**编译期注入**——`create_deep_agent(subagents=[...])` 把子 Agent 清单**写死进图结构**，**没有运行时向已编译图追加 subagent 的 API**。

**所以"自动附加"的实现 = 触发图重建**：
```
1. 用户新建子 Agent C
2. 系统使「所有开启了委派开关(enable_subagents=true)的主 Agent」图失效
3. 主 Agent 下次对话时重新构建图
4. 图重建时 get_subagents() 重新聚合 → C 自动出现在委派列表
5. 主 Agent 的 LLM 即可通过 task 调用 C
```

**推荐动作**：`create_agent` 时对"所有 `enable_subagents=true` 的 agent"触发图失效，同时**补全 SubAgent 配置映射**（一并解决"动态发现"与"专精委派"两个问题）。

#### ⑤ 通讯方式：同步与异步两条路径

| 路径 | 机制 | 特征 | 适用 |
|------|------|------|------|
| **同步委派（默认）** | `task` 工具一次性交接 | 无状态、单次回传、阻塞 | 快速子任务（多数场景） |
| **异步远程（可选）** | Agent Protocol：`start/check/update/cancel/list_async_task` 5 工具 | 有状态（独立线程）、可中途纠偏、可跨部署 | 长任务、需中途干预 |

- 异步子 Agent 需部署 Agent Protocol 服务器（LangSmith 部署 / 自建 FastAPI / ASGI 同进程），作为 V1.0+ 增强能力，**不在 MVP**。
- **多主对等协作**：SDK 无内置协议，需借 Agent Protocol 或 LangGraph StateGraph 自行编排，**本阶段不做**。

#### ⑥ 一个完整委派时序（端到端走查）

```
 用户 ──(1)选择主Agent，发消息──▶ 主Agent
                                   │
        (2)图构建时注入 subagents 清单（内置 general-purpose + 自定义）
                                   │
        (3)主Agent LLM 判断要委派给"翻译"
                                   │ task(name="翻译", description="翻译这段英文")
                                   ▼
                             临时子Agent「翻译」
                              （干净上下文，独立运行，可多次调工具）
                                   │
                                 只回传 1 条最终结果（ToolMessage）
                                   ▼
        (4)主Agent 收到结果，整合后 ──(5)回复──▶ 用户
        (6)临时子Agent「翻译」实例销毁（无状态）
```
> 注意：子 Agent 的中间过程不进入主 Agent 上下文（**上下文隔离**），这是协作价值的关键。

#### ⑦ 产品边界声明

- **MVP 承诺**：多 Agent 创建 + 同步委派（`task`）+ 主 Agent 统一调度（含内置 general-purpose）+ 动态发现 + 补全 SubAgent 配置。
- **V1.0 增强**：异步子 Agent（Agent Protocol）、可中途纠偏的长任务。
- **本阶段不做**：多主对等协作、子 Agent 再嵌套（SDK 语义不支持）。

### 5.3 当前差距 → 产品待办（与架构诊断对齐）

| 差距 | 产品影响 | 优先级 |
|------|----------|--------|
| **HITL 无运行时闭环** | "高危操作要审批"只是空配置，实际会挂起/超时 → 动摇"安全可控"价值主张 | 🔴 P0 |
| **SubAgent 仅 3 字段**（无独立 tool/model/permission） | 无法实现"审计子代理只读""简单子任务用便宜模型" → 削弱协作与成本价值 | 🔴 P0 |
| **委派单向**（仅 default 可委派） | 无法组建真正的多向协作团队 | 🟠 P1 |
| **description 模板化** `Agent: xxx` | LLM 无法判断何时委派给谁 → 协作命中率低，直接打击 Aha Moment | 🟠 P1 |
| **无认证/多租户** | 无法多用户使用、无角色权限 → 卡住企业采用 | 🟠 P1 |
| **无配置版本化/回滚** | 改错配置无法回退 → 治理缺口 | 🟠 P1 |
| **无流式** | 对话/委派过程无实时反馈 → 体验欠佳、debug 黑盒 | 🟡 P2 |
| **沙箱为降级占位** | "沙箱执行"名不副实 → 能力声明失真 | 🟡 P2 |

## 6. 业务规则与边界

### 6.1 关键业务规则（BR）

- **BR1 默认最小化**：新建 Agent 默认只开最小工具集、默认关闭委派（安全优先，逐项 opt-in）。
- **BR2 工作区隔离**：每个 Agent 只能读写自己的工作区（`virtual_mode=True`），除非权限规则显式放开。
- **BR3 防自委派**：任何 Agent 不能被注入到自己的子代理列表，避免无限递归。
- **BR4 委派只回结果**：子代理只回传最终文本到主对话，中间过程不进入主上下文。
- **BR5 危操必审批**：配置为 `interrupt` 的操作，必须经人工决策后才继续（目标态）。
- **BR6 密钥不进库**：API Key 等敏感信息存环境变量中心，不写入 agent.json / 仓库 / 日志明文。
- **BR7 变更需生效**：修改模型/工具/权限后需重建图生效；修改系统提示需清 checkpoint 让旧会话读到。

### 6.2 非功能需求（NFR）

| 类别 | 目标 |
|------|------|
| **安全** | 工作区逃逸阻断；权限最小化；敏感信息脱敏；关键操作可审计 |
| **性能** | 多 Agent 并发对话不互相阻塞（当前全局锁是瓶颈，见架构报告 §3.9） |
| **可扩展性** | 支持数百 Agent；状态/成本按 Agent 隔离可归因 |
| **可靠性** | 配置与对话可备份恢复；崩溃不损坏数据（原子写已具备） |
| **可用性** | 非技术用户 10 分钟建 Agent 并成功对话 |

## 8. 竞品分析

### 8.1 竞品地图（按"多 Agent 程度 × 治理程度"）

```
治理/安全 高
    │
    │   AgentCore(目标)●           ● LangSmith / 企业 Agent 平台
    │
    │   ● Copilot Studio / Dify(多Agent)   
    │
    │                    ● 单Agent工具 / 个人Chatbot
    │
    └───────────────────────────────────────▶ 多Agent协作 高
```

### 8.2 差异化对比

| 维度 | AgentCore | 个人 Chatbot / 单 Agent | Dify / 低代码 Agent 平台 | LangSmith 等 |
|------|-----------|-------------------------|--------------------------|--------------|
| 多 Agent 协作 | ✅ 原生（跨 Agent 委派） | ❌ | 🟡 多为流程编排 | 🟡 偏部署侧 |
| 零代码上手 | ✅ | ✅ | ✅ | ❌ 偏开发者 |
| 安全治理（权限/审批/隔离） | ✅ 主打 | ❌ | 🟡 有限 | ✅ |
| 开放底座 | Deep Agents（LangGraph） | 各自为政 | 自有引擎 | LangChain 系 |
| 强项 | **多 Agent 协作 + 治理** | 简单 | 低代码工作流 | 可观测/部署 |

### 8.3 结论

AgentCore 的**差异化空位**是：**「零代码 + 多 Agent 协作 + 企业治理」三角交集**。竞品大多只占其中一角或两角（Dify 偏工作流、LangSmith 偏开发者观测）。守住"业务用户也能编排 AI 团队、且安全可控"这条主线，即可建立壁垒。

## 9. 成功指标与风险

### 9.1 指标体系

| 层级 | 指标 | 目标（示意） |
|------|------|--------------|
| **北极星** | 每周活跃委派次数 | 反映"多 Agent 协作"核心价值被持续使用 |
| 激活 | 新建 Agent 数 / 首次成功对话率 | 首日 ≥ 1 个 Agent + 1 次成功对话 |
| 粘性 | 会话留存 / 日均对话轮次 | D7 会话留存 ≥ 30% |
| 协作 | 委派成功率 / 子代理节省上下文比 | 委派成功率 ≥ 80% |
| 治理 | 高危审批通过率 / 安全事故数 | 审批闭环接通率 100% |
| 成本 | 每任务 token / 按 Agent 成本归因 | 可归因覆盖率 100% |

### 9.2 关键风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **HITL 长期不接通** | "安全可控"沦为空话，企业不敢用 | V0.5 第一优先，单独立项 |
| **SubAgent 无法收窄权限/模型** | 协作时子代理越权/成本失控 | V0.5 补齐 4 个核心字段 |
| **委派描述太弱** | LLM 委派命中率低，协作价值体验不到 | description 智能生成，纳入验收 |
| **无认证** | 无法多人/多角色使用 | V1.0 引入认证与 RBAC |
| **依赖本地私有 SDK 路径** | 换环境无法部署 | 依赖改为 git tag/私有 PyPI（工程项） |
| **无流式** | 长任务反馈差、debug 黑盒 | V1.0 引入 SSE |
